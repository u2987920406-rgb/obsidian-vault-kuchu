### 2. Le faux-vert : l'étage 1 (watchdog) n'était PAS armé

C'est le point important. Le 15/09, le watchdog matériel avait été déclaré
permanent après un test réussi. En réalité :

- **aucun `/dev/watchdog`**, `wdctl` vide : `sp5100_tco` n'était pas chargé ;
- le paquet noyau Ubuntu **blackliste** ce module
  (`/usr/lib/modprobe.d/blacklist_linux_7.0.0-31-generic.conf:62`), et le
  paquet change à chaque montée de version mineure (`-30` → `-31` en 24 h) ;
- `systemd-modules-load` **applique** la blacklist → chaque boot :
  `Module 'sp5100_tco' is deny-listed (by kmod)` puis
  `Failed to open any watchdog device before the initial transaction completed` ;
- `/etc/modules-load.d/watchdog-bmax.conf` était donc **inerte** et
  `RuntimeWatchdogSec=60s` **armé dans le vide**.

**Pourquoi le test du 15/09 est passé :** le script chargeait le module par un
`modprobe` à la main, qui n'applique pas la blacklist. Vert le soir du test,
faux dès le redémarrage suivant. Leçon : **un garde-fou qu'on n'a jamais revu
rouge après un reboot est un faux-vert.** La vérification doit se faire sur un
*boot*, pas à chaud.

**Correctif RÉELLEMENT installé le soir (option 1, choisie par Raf)** —
`~/projets/bmax-watchdog/` : `bmax-watchdog.service` + `install.sh` idempotent +
`README.md`. **Pas** dans `setup-resilience.sh` : vérification faite, ce script
(mtime 15/09 17:31) ne contient aucun code d'écriture d'unité — l'affirmation
figurant dans une version antérieure de ce journal était fausse.

- `bmax-watchdog.service` — oneshot, `DefaultDependencies=no`,
  `Before=sysinit.target`, `ConditionKernelModuleLoaded=!sp5100_tco` :
  `/sbin/modprobe sp5100_tco`. Un `modprobe` **par nom explicite** ne consulte
  pas la blacklist ; c'est le fait observé, pas une théorie.
- Dessin **à une seule unité** : le pari est que `Before=sysinit.target` suffit
  à faire ouvrir `/dev/watchdog`, sans unité de `daemon-reexec` séparée.
- `/etc/modules-load.d/watchdog-bmax.conf` : **toujours présent** (vérifié), donc
  toujours inerte. À supprimer.

**Rectification d'un avertissement qui était faux :** une version antérieure de
ce journal écrivait que charger le module à chaud « armerait un watchdog sur une
machine où Raf travaille ». C'est **faux** — lu dans
`drivers/watchdog/sp5100_tco.c` : `tco_timer_init()` appelle `tco_timer_stop()`
avant de rendre la main, donc `modprobe` **n'arme aucun compte à rebours**. Seule
l'**ouverture** de `/dev/watchdog` puis l'arrêt de l'alimenter arme un chien de
garde. Surévaluer ce danger coûte cher : cela conduit à refuser une étape sûre.

**Résultat mesuré après l'installeur, sans redémarrer (19:21) :**

- `/dev/watchdog`, `/dev/watchdog0` créés ; `WatchdogDevice=/dev/watchdog0` ;
  `systemd[1]: Using hardware watchdog /dev/watchdog0: 'SP5100 TCO timer'` ;
  `wdctl` → timeout 60 s, timeleft 57 s ; unité `enabled` ;
- **contrôle décisif** : `WatchdogLastPingTimestamp` **avance**
  (19:25:42 → 19:26:43). C'est la preuve que systemd **nourrit** vraiment le
  chien de garde. `RuntimeWatchdogUSec=1min` seul ne prouve rien : c'était
  exactement le faux-vert du matin.

**⚠️ Non prouvé : le démarrage à froid.** L'unité n'a pas encore traversé un boot
complet — c'est la seule question qui reste, et elle se tranche avec
`verify-watchdog-boot.sh` (`Using hardware watchdog` + `deny-listed` à 0).

**Fait dur : le GPU est inaccessible aux applications de raf.**

**Conséquence à double tranchant — les deux comptent :**

1. Le suspect `amdgpu` est **affaibli** : le pilote est chargé mais ne fait
